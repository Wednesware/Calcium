# Calcium — Implement an Independent Native Python Runtime

You are working on **Calcium**, Wednesware's Python-to-C compiler.

## Primary objective

Transform Calcium from a compiler that primarily generates C code backed by CPython into a **genuinely native Python-to-C compiler with its own runtime**.

**The ultimate goal is to compile ordinary Python programs into fast, standalone native executables without requiring CPython, libpython, Python headers, or an installed Python interpreter at runtime.**

Performance is Calcium's primary purpose. Compatibility and correctness are essential, but the compiler must not achieve compatibility merely by forwarding ordinary Python operations to CPython.

This is a substantial architectural project. Implement it incrementally, but deliver actual working code, tests, and benchmarks rather than only architectural documentation.

## 1. Inspect the existing codebase

Before modifying anything:

- Examine Calcium's frontend, parser, AST handling, intermediate representation, optimizer, C generator, runtime, module loader, and build pipeline.
- Identify which components can be reused by a CPython-independent backend.
- Identify every place where generated code depends on `Python.h`, `PyObject`, `PyNumber_*`, `PyImport_*`, `Py_Initialize`, and other CPython APIs.
- Examine existing optimization levels, type inference, scalar kernels, diagnostics, fallback mechanisms, and tests.
- Preserve the existing working compiler and its public API wherever practical.

Do not rewrite working frontend infrastructure unnecessarily.

## 2. Introduce two execution backends

Implement two explicitly selectable backends:

```bash
ca build program.py --backend native
ca build program.py --backend cpython
```

### Native backend

- Generate standalone C11 code.
- Use Calcium's own runtime, written in C.
- Do not link against libpython.
- Do not include `Python.h`.
- Do not invoke an installed Python interpreter.
- Do not silently execute Python source or bytecode through CPython.
- Compile supported Python operations into native C and native runtime operations.
- Reject unsupported features with clear diagnostics.

### CPython backend

Preserve the existing implementation for compatibility.

It should continue supporting existing projects, third-party Python packages, and the current fallback system.

**Keep CPython as the default backend initially**, until the native backend has sufficient compatibility and reliability.

Native mode must never silently fall back to CPython.

## 3. Implement Calcium Runtime (CaRT)

Create a separate native runtime library, provisionally named `CaRT`.

Suggested structure:

```text
calcium/
  backend/
    native/
    cpython/
  runtime/
    native/
      include/
      src/
        values.c
        integers.c
        floats.c
        strings.c
        containers.c
        memory.c
        functions.c
        objects.c
        exceptions.c
        modules.c
        builtins.c
```

Adapt this structure to the existing repository rather than duplicating established abstractions.

### Value representation

Implement a flexible Python-compatible value representation supporting:

- `None`
- `bool`
- `int`
- `float`
- `str`
- `bytes`
- `list`
- `tuple`
- `dict`
- `set`
- Functions
- User-defined objects

Use efficient tagged values, unboxed representations, or heap-allocated objects as appropriate.

Avoid allocating heap objects for every primitive operation.

Preserve Python semantics, including arbitrary-precision integers, truthiness, equality, identity, hashing, and exception behavior.

Implement features incrementally; unsupported types must produce explicit diagnostics rather than incorrect results.

### Memory management

Implement a correct ownership and lifetime model.

Choose and document an appropriate strategy, such as reference counting with cycle collection or a tracing garbage collector.

The implementation must eventually support cyclic containers, shared references, object finalization, and safe exception unwinding.

Prioritize correctness before optimizing allocations.

## 4. Generate genuinely native C

The native backend must not simply replace CPython API calls with equivalent generic runtime calls everywhere.

Use type inference, specialization, and escape analysis to generate direct C operations wherever semantics permit.

For example:

```python
def square(x: int) -> int:
    return x * x
```

Should produce a specialized native function operating on machine integers when safe, with guards or appropriate handling for Python's arbitrary-precision behavior.

Optimize:

- Integer and floating-point arithmetic
- Comparisons and boolean operations
- Local variable access
- Conditions and loops
- Function calls and recursion
- Constant expressions
- Built-in operations
- Container access
- Temporary object allocations

Prefer direct native calls between compiled functions.

Avoid boxing and unboxing at every function boundary.

Use a generic native runtime path when static specialization is not possible.

**Never sacrifice Python semantics for speed without an explicitly documented opt-in mode.**

## 6. Optimize startup aggressively

Calcium currently shows these approximate results on an empty program:

| Runtime | Startup |
|---|---|
| CPython | 7.0 ms |
| CPython `-S` | 5.3 ms |
| Calcium CPython backend | 7.8 ms |

The native backend should avoid interpreter initialization entirely.

For a minimal `pass` program, aim for:

- Startup below 1 ms on the reference machine, if achievable.
- Minimal memory consumption.
- No unnecessary runtime initialization.
- No dynamic loading of libpython.
- No filesystem searches for Python packages.

Treat these as performance targets, not guaranteed results.

The native runtime should initialize only the functionality the executable actually needs.

## 7. Preserve and expand optimization levels

Keep Calcium's existing O0–O3 interface.

All optimization levels must preserve correct Python behavior.

Suggested direction:

- **O0:** Correct baseline native lowering.
- **O1:** Dead-code elimination, constant propagation, basic control-flow optimizations.
- **O2:** Type specialization, scalar unboxing, optimized calls and loops.
- **O3:** Aggressive interprocedural optimization, safe inlining, escape analysis, allocation elimination, and optional link-time optimization.

Implement only optimizations that can be validated.

Do not advertise optimizations that are merely planned.

## 8. Make native compilation observable

Extend the optimization reporting system to show:

- Functions compiled to specialized C
- Functions using generic CaRT operations
- Boxing and unboxing operations
- Dynamic dispatch operations
- Heap allocations where statically identifiable
- Native-to-native calls
- Optimization decisions
- Unsupported language features

Distinguish static analysis from measured runtime behavior.

Provide an option to retain generated C for inspection.

Measure wall-clock time, CPU time, peak RSS, and executable size.

Benchmark compilation time separately from executable runtime.

Compare output, return values, exceptions, and observable side effects against CPython before comparing performance.

Use multiple runs and report variation.

Never claim that a benchmark demonstrates a general speedup when it measures only one workload.

## 10. Tests and compatibility

For every implemented feature:

- Add unit tests.
- Add integration tests that compile and execute native binaries.
- Compare behavior with CPython.
- Test overflow, negative values, empty containers, recursion, and error paths.
- Test memory ownership and cleanup.
- Use sanitizers where supported.
- Ensure native executables do not require Python at runtime.
- Ensure the existing CPython backend continues passing its tests.

The native backend must fail clearly on unsupported features.

It must never silently produce incorrect results.

## Final design principle

**Calcium must become a compiler that executes Python semantics efficiently through native code, not merely a translator that delegates Python execution to CPython.**

The goal is to make Python programs faster while retaining Python as the source language.

Prioritize correct native execution, minimal runtime overhead, efficient memory representations, and measurable performance improvements.
