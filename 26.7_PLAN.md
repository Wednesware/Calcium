# Calcium / Bonemarrow — CLI Integration and Native Package Support

## Objective

Extend Calcium's Bonemarrow (`bmrw`) backend with native Python package and module support, while improving the CLI experience.

Calcium is the public-facing API and CLI. Bonemarrow is its independent Python-to-C compiler and runtime.

**The primary goal is to compile multi-file Python applications into standalone native executables without CPython.**

Implement working functionality, tests, and documentation. Do not merely rename the existing CPython backend or route imports through CPython.

## 1. Backend selection

Use Bonemarrow as Calcium's default backend.

Support:

```bash
ca test.py
ca test.py --use bmrw
ca test.py --use cpython
ca test.py --bmrw
ca test.py --cpython
```

Preserve existing `--backend native` and `--backend cpython` options as compatibility aliases.

Requirements:

- `bmrw` selects the independent CaRT-based native backend.
- `cpython` selects the existing CPython compatibility backend.
- Conflicting selections must produce clear errors.
- Unsupported native features must never silently fall back to CPython.
- Maintain consistent selection across CLI commands and Python APIs.

## 2. CLI logging and identity

Normal compilation should remain quiet:

```text
$ ca test.py
build/test/test
```

With `-v` or `--verbose`:

```text
calcium: using Bonemarrow (bmrw)
calcium: optimizing at O3
calcium: compiling test.py
calcium: linking executable
calcium: built build/test/test
```

Use the actual selected optimization level and report only stages that occur.

Add an optional `--fancy` mode:

```text
calcium: awakening Bonemarrow...
```

Only print this when explicitly requested.

Compiled executables must never print startup messages or compiler logs automatically.

Keep diagnostic and progress output separate from application stdout and machine-readable output.

Update `ca --info` to identify Calcium, Bonemarrow, available backends, and their actual versions.

## 3. Native multi-file project support

Currently, Bonemarrow 26.6 supports standalone Python scripts but rejects packages and modules.

Remove this restriction by implementing genuine native module compilation and linking.

Support:

```bash
ca main.py
ca my_package/
ca my_package --use bmrw
ca --module my_package
ca --module my_package.cli
```

Use existing project-root and include-path options where applicable.

Support project structures such as:

```text
myproject/
├── main.py
└── mypackage/
    ├── __init__.py
    ├── mathutils.py
    └── helpers.py
```

Example:

```python
# mypackage/mathutils.py

def square(x: int) -> int:
    return x * x
```

```python
# main.py

from mypackage.mathutils import square

print(square(12))
```

Bonemarrow should compile and run this program without CPython.

## 4. Native import system

Implement a native module system supporting:

- `import module`
- `import package.module`
- `from module import name`
- `from package import module`
- Import aliases
- Relative imports
- Package `__init__.py`
- Package `__main__.py`
- Module-level variables and functions
- Cross-module function calls
- Module namespaces
- Import caching
- Circular imports
- Correct initialization order

Reuse Calcium's existing project discovery, dependency graph, parsing, IR, and source resolution where possible.

Do not implement native imports by calling CPython's importlib or embedding Python source.

Each compiled module should have a native initialization function and a runtime module object or equivalent representation.

Module initialization must happen once per module per process, with correct handling of partially initialized modules and import failures.

## 5. Native compilation and linking

Compile project modules into separate C translation units where practical.

Example conceptual output:

```text
build/myproject/
├── generated/
│   ├── main.c
│   ├── mypackage_init.c
│   ├── mypackage_mathutils.c
│   └── mypackage_helpers.c
└── myproject
```

Actual paths may differ according to the existing build system.

Requirements:

- Preserve Python module namespaces.
- Avoid C symbol collisions.
- Support calls between native modules.
- Link against CaRT, not libpython.
- Avoid generating Python source or bytecode for runtime execution.
- Preserve Python-compatible import side effects and initialization order.
- Keep generated C inspectable through existing options.

Add incremental compilation or caching if the existing infrastructure can be reused safely, but prioritize correctness first.

## 6. Native runtime extensions

Package support requires additional runtime functionality.

Implement the minimum necessary support for:

- Module objects and namespaces
- Global bindings
- Imported names
- Cross-module references
- Module initialization states
- Import-related errors
- Module cleanup and ownership
- Garbage collector roots for loaded modules

Do not treat imports as simple textual inclusion.

Modules must retain separate global namespaces and correct Python-style initialization behavior.

## 7. Expand native language compatibility

Native package support is only useful if ordinary package code can execute.

Extend Bonemarrow's supported language features incrementally, prioritizing:

1. Lists, tuples, dictionaries and sets.
2. Indexing, slicing and iteration.
3. Default arguments, keyword-only arguments and variadic calls.
4. Classes, instances, attributes and methods.
5. Exceptions and structured exception handling.
6. Closures and decorators.
7. Standard-library functionality and native library bindings.

For each feature, add correctness tests against CPython.

Maintain efficient native representations and avoid unnecessary boxing.

Do not compromise Python semantics simply to pass a benchmark.

## 8. Discribe compatibility milestone

Use Discribe as a long-term real-world compatibility target.

The intended eventual command is:

```bash
ca discribe -O3
```

With Bonemarrow selected by default.

However, Discribe depends on functionality beyond package imports, including classes, GUI libraries, and CPython extension modules.

**Do not claim Discribe is natively compatible until it actually builds and runs without CPython.**

Track the remaining blockers through explicit diagnostics.

If native compilation fails, show a useful message:

```text
calcium: error: Bonemarrow does not yet support feature X
calcium: hint: use --cpython for compatibility
```

Do not silently switch to CPython.

## 9. Performance requirements

Preserve Bonemarrow's startup and memory advantages.

Existing reference measurements for a standalone `pass` program:

- Native Bonemarrow: approximately 0.36 ms startup.
- CPython: approximately 7.15 ms startup.
- Native Bonemarrow: approximately 4.3 MiB measured memory.
- CPython: approximately 11 MiB measured memory.

These are environment-specific measurements, not universal guarantees.

Add benchmarks for:

- Single-file startup
- Package startup
- One-module imports
- Multi-module imports
- Cross-module function calls
- Repeated imports
- Circular imports
- Package initialization
- Large package dependency graphs

Compare native Bonemarrow, Calcium's CPython backend, and ordinary CPython.

Measure compilation time separately from executable runtime.

Do not introduce unnecessary runtime initialization overhead for standalone scripts.

## 10. Testing

Add automated tests covering:

- Absolute and relative imports
- Nested packages
- Module globals
- Aliased imports
- Circular dependencies
- Repeated imports
- Module initialization order
- Import errors
- Module namespace isolation
- Cross-module recursion
- Package entry points
- Garbage collector ownership of module values
- Native binaries running without Python installed
- CLI backend selection and verbose/fancy logging
- CPython backend regression compatibility

Compare program output, exit status, and relevant side effects against CPython.

Use sanitizers for memory-related tests where supported.

## 11. Implementation sequence

Implement in manageable stages:

**Stage A — Native project infrastructure**

Accept directory/package inputs and compile multiple Python files into one native executable.

**Stage B — Module runtime**

Implement module namespaces, initialization, import caching and linking.

**Stage C — Import semantics**

Implement absolute, relative, aliased, repeated and circular imports.

**Stage D — Language compatibility**

Expand containers, functions, classes and other features needed by real packages.

**Stage E — CLI integration**

Complete Bonemarrow naming, backend selection, verbose messages, optional fancy mode and diagnostics.

**Stage F — Validation**

Run differential tests, sanitizers, benchmarks and CPython regression tests.

Do not stop at planning. Implement and validate as much of this sequence as possible, reporting unfinished stages accurately.

## 12. Deliverables

- Native package and module compilation.
- Native import handling without CPython.
- Multi-module C generation and linking.
- CaRT module runtime extensions.
- Updated CLI selection and logging.
- Automated compatibility tests.
- Package performance benchmarks.
- Updated documentation.
- Clear remaining-feature and Discribe-compatibility reports.

## Core principle

**Calcium is the interface. Bonemarrow is the independent native execution engine.**

The goal is not to make Python programs look like C. The goal is to make them execute efficiently as native programs while preserving Python behavior.

Build genuine native functionality, never disguise CPython fallback as native execution, and keep the existing CPython compatibility backend available explicitly.
